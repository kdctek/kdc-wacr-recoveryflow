# Changelog

All notable changes to RecoveryFlow by WA.cr will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

Each entry opens with a plain-language statement of what changed for the person
affected, followed by the detail.

## [Unreleased]

### Added

- **RecoveryFlow can now send a recovery email, not only a WhatsApp message.** The email channel has existed since the compliance settings shipped -- it had consent, opt-outs, eligibility and a switch on the settings screen -- and nothing behind any of it could actually send. It can now. A workflow step set to email is written by the merchant themselves, subject and body, with the same placeholders the WhatsApp templates use; there is no template to get approved and nobody to approve it. Every message carries the business's postal address and a working unsubscribe link, appended by the plugin rather than left to the wording, because the first thing anybody does to a message template is shorten it and those two things are what make commercial email lawful to send. The message is plain text on purpose: a recovery email is a short note with one link in it, and HTML would buy a customer nothing while costing an escaping surface, a layout to maintain in every mail client, and remote images that Gmail fetches through its own proxy the moment the message is opened.
- **Recovery email needs no WA.cr plan, and no API key at all.** It leaves through the site's own mail configuration, so it goes out by the same route and with the same identity as the shop's order emails -- a site that has set up SMTP, or a sending domain with SPF and DKIM, has already answered that question and the plugin does not second-guess it. It costs nothing and never touches WA.cr's API, which also means the WhatsApp rate allowance no longer holds it back: a free message was previously deferred whenever a paid channel hit its ceiling, which is exactly the moment a busy shop most wants the reminders going out. A workflow built only from email steps runs on a workspace that cannot send WhatsApp from WordPress at all.
- **When an email cannot be sent, the site now records why.** WordPress answers only false and says nothing, which on a shop whose SMTP credentials have expired is the difference between fixing it this morning and noticing in a fortnight. The reason is captured and kept as a code -- never the message, which carries the recipient's address -- and a transport that raises instead of returning is caught rather than taking the whole background pass down with it. A refused send is retried with backoff, because the usual cause is the site's own mail briefly failing and none of it is about the customer.

- **A contact detail can now be asked for before the checkout.** Most shoppers who abandon never reach the checkout, so until now the plugin recorded a great many baskets it had no way to act on. Two new places can ask, each with its own switch and **both off until you turn them on**: a short "save this basket" form below the basket, and a field beside the "add to basket" button on a product page. Where the site asks for consent, the tick-box appears with them, using the same wording and recording the same thing the checkout records — a shopper is never opted in by having typed a number. Both work with scripts blocked, and both work on a block-based basket and product page as well as the older shortcode ones. Neither will overwrite something you already gave with a blank: leaving the basket field empty does not erase the number typed on the product page.

- **The checkout's phone number can be made compulsory.** WooCommerce ships it optional, so an order can complete with no way to reach the person. This is one switch instead of a snippet, and it applies to the classic and the block checkout alike because both read the same WooCommerce setting. It is off by default and the help text says plainly what it costs: somebody who will not give a number cannot buy from you, so it saves lost sales and loses some completed ones. RecoveryFlow filters that setting rather than writing it — switch this off and WooCommerce's own answer comes straight back, and deactivating the plugin cannot leave a requirement behind that nobody chose.

- **The recovery queue can now be worked in bulk.** Stopping eleven recoveries meant opening eleven recoveries. Each row now carries a tick-box and the queue offers the same four things the single-recovery screen does -- stop these, try these again, stop their links working, never message these customers again. Nothing about what is allowed changes: every ticked recovery goes through exactly the code one recovery goes through, so a recovery that would be refused on its own screen is refused here for the same stated reason, and the refusals are listed by reference rather than counted, because "three were refused" is not something anyone can act on and three references are. The tick-boxes appear only for somebody who is allowed to change the queue; reading it and working it are separate permissions, and the read-only view stays read-only. As everywhere else in this plugin, the bulk form is a POST and it works with scripts blocked.

- **The accessibility of every screen is now checked, on every screen, instead of described.** RecoveryFlow's admin has been built to WCAG 2.2 AA as a minimum since the first screen landed, and the command meant to prove it -- `npm run a11y` -- had never visited a page: it was configured with an empty list of addresses and no way to log in, so it passed against nothing while five slices of screens shipped. There is now a real run. It seeds a site with recoveries in every state that renders differently, logs in, and checks all twenty-four screens -- every admin screen, every settings tab, a deeplinked field, and the five public pages a customer sees: the unsubscribe page, the page after that button has been pressed, a link that no longer works, a product page, and a basket the run fills by pressing the real "add to basket" button. It fails on any WCAG 2.2 AA finding, then checks the same screens again at AAA and prints what it finds without failing, because most of what AAA objects to is core WordPress's own colours on core's own components and a gate that can never go green is a gate somebody turns off. A second command walks every screen with the Tab key: no keyboard traps, nothing that takes focus while invisible, every stop paints something when focused and announces as something. Both run in continuous integration, and the test suite fails if a screen this plugin registers is missing from the list -- a suite that checks most of the screens is the same defect as one that checks none, only harder to notice.

### Fixed

- **The workflow editor no longer offers a choice that was never real.** Every step that sent a WA.cr template also carried a second dropdown asking whether to send it over WhatsApp or email -- and a WA.cr template cannot arrive as email. Whichever was picked, a WhatsApp message went out and was recorded and billed as one. The channel is now stated rather than asked, taken from the action the step will actually run, and a channel posted straight past the form is ignored instead of being stored as a step whose two halves contradict each other. A workflow built only from email steps also no longer claims to need the WA.cr plan that includes the developer API: it needs no API key at all, and saying otherwise would have stopped a merchant on the Lite plan from building one.

- **The mail proxies that open a link before anybody has read it are no longer counted as customers.** Gmail, Yahoo and Bing all fetch what arrives in a message, and a recovery link fetched that way was being recorded as somebody tapping it. They are recognised now, alongside the chat and social crawlers already known. What still cannot be recognised is a corporate link scanner -- Microsoft's Safe Links and the equivalents from Proofpoint, Mimecast and Barracuda open every URL in an incoming message behind an ordinary browser's user agent, and nothing in a user agent tells one of those from a person. Guessing at their names would look like coverage while catching nothing, so the documentation says plainly that a click figure on the email channel is softer evidence than one on WhatsApp. What that scanner cannot do is anything that matters: following a recovery link never marks somebody as having replied, and the unsubscribe refuses to act on a plain visit, so a scanner opening every link in a message cannot unsubscribe the person it was protecting.

- **A workflow step now sends on the channel it says it sends on.** The step editor offered a channel for each message and nothing that actually sent one ever read it: both send actions recorded every message as WhatsApp whatever the step said, and the eligibility check asked whether the customer could be reached on *any* channel rather than on the one the step had chosen. So a shop that switched the email channel on and built a step to use it got WhatsApp instead -- and a customer who had given an email address and no phone number could be picked out as reachable and then have a WhatsApp message attempted for a number that was never there. An action now declares the channel it can send on, the step is refused outright if it names a different one rather than being sent over whichever of the two was read last, and consent, opt-out and eligibility are all decided about the channel the step actually uses.

- **Two checks that reported success while checking nothing have been stopped.** Continuous integration ran a job called "Unit tests" on every release, and the four PHPUnit suites it ran are empty -- so it reported "No tests executed!", exited successfully, and put a green tick for coverage that did not exist on every build since the first release. `npm run a11y` did the same thing for accessibility: it is configured for WCAG 2.2 AAA and given no page addresses to visit, so it passed against zero screens while every admin screen in the plugin shipped unchecked. Neither is a small thing to leave standing, because a green tick is read as an answer and is what somebody points at instead of checking. The empty job is gone rather than left to be misread; the accessibility command now refuses an empty list instead of passing; and the test suite asserts both in each direction, so the first PHPUnit test written fails the build until the job is restored, and listing the first screen fails it until the documentation stops saying the suite is unbuilt. The documentation that described all five suites, and an accessibility run with a login step, in the present tense now says plainly which of them exist. What is actually tested is unchanged: it is the smoke suite, which runs on two PHP versions on every push, and it is now the first row of the table instead of missing from it.

- **An empty recovery queue no longer contains a form nobody can submit.** Searching for something that matches nothing left a form on the page with no button in it, which is a dead end for anyone moving through the page by keyboard. The form is now only rendered when there is something to act on.

- **Some controls in wp-admin had two of the same button, and two elements with the same identity.** Every row of the recoveries queue carried the "Show more details" toggle twice -- the column added one and WordPress added another -- so anybody moving through the queue with a keyboard tabbed past a duplicate on every row, and a screen reader announced it twice per row with the second doing exactly what the first had done. Separately, three screens put more than one element with the identity `_wpnonce` on the page: one recovery's screen renders a form per action, and the WA.cr and Privacy settings tabs each render their own forms alongside the settings form. Nothing pointed at those identities yet, which is the only reason nothing had broken -- a label, a description or a link to a field resolves to the first match, so a duplicate is a hazard waiting for the next person to add one. Neither was reported by either accessibility checker: two buttons with the same name are valid HTML, and the duplicate identity is on a hidden field. Both were found by reading the markup the new accessibility run put in front of us, which is most of the argument for having it.

- **The one colour this plugin chose that fell short of its own standard has been corrected.** The "Link" anchor beside each settings section heading inherited WordPress's link blue, which measures 4.93:1 against its background -- comfortably past the 4.5:1 that AA requires, and short of the 7:1 this plugin's accessibility documentation claims for anything it adds itself. It is now core's darker link colour at 9.2:1. It was the only one: of the 380 findings the enhanced-contrast pass reports, every other one is a colour core WordPress chose for a core component, which this plugin does not get to change and should not claim to have fixed.

- **The unsubscribe link in a recovery email kept working only until the customer bought something.** Every recovery email carries an unsubscribe link, and the plugin refuses to send one at all unless that link is set to outlive the message by thirty days, because that is what the law asks of commercial mail. It was not outliving anything. The unsubscribe and the "return to your basket" link are the same link, and that link is deliberately killed the moment an order is placed -- correctly, since a basket that has been bought should not be rebuilt. Both were being judged by that one rule, so the customer who came back and bought was the only customer who could not unsubscribe from the mail that brought them: they were shown the same page as somebody clicking a link that never existed, and nothing was recorded. The two are now judged separately. Buying closes the basket link and leaves the unsubscribe open; expiry still closes both, which is what keeps the thirty days a real window rather than a claim. Nothing about the shopper's privacy changes -- a request to stop was already recorded against the person rather than against the one reminder, which is why it works at all for somebody whose recovery has long since finished.

## [0.1.0] - 2026-09-08

First release. RecoveryFlow detects abandoned journeys across WordPress
commerce, works out whether the person may lawfully be contacted, and recovers
them through WA.cr on WhatsApp. An active WA.cr account is required; the plugin
cannot message anyone on its own.

### Added

- **A WA.cr Auto Flow can now tell this site that somebody replied STOP.** Add a webhook step to your flow, point it at the address on Settings &rsaquo; WA.cr, and give it the secret shown there. A customer who unsubscribes inside your flow is then stopped here immediately, on every contact detail they have given and across every open recovery, instead of whenever the next background pass happens to look -- and every minute of that delay was a minute in which another reminder could reach somebody who had asked to be left alone. A reply that is not an unsubscribe can be reported too, and marks the recovery engaged without closing it, because somebody asking how much postage costs has not finished their order. **This is not what the plan described, and the difference is deliberate.** The plan asked for a receiver for delivery statuses and replies, checking a signature. WA.cr has no way to notify a URL when a message is delivered or read -- which is exactly why this plugin polls for that instead -- and the one thing in WA.cr that can call a URL does not sign what it sends. A receiver checking a signature would have refused every real request while looking thorough, so it authenticates with a shared secret, which is what the platform can actually present. The secret is shown once and only its fingerprint is kept; the endpoint refuses everything until one exists, answers the same way whether a secret was wrong or was never set, and quietly ignores the same event arriving twice.

- **A customer who only ever gave a phone number can now be forgotten.** WordPress's privacy tools find somebody by email address. RecoveryFlow exists to recover people over WhatsApp, so a large share of the customers it holds typed a phone number at the checkout and never an address -- and for those people there was nothing to type into core's box at all. The honest answer to "please delete my data" from one of them was to go into the database. Settings > Privacy now takes the number instead, and understands it written the way a customer reads it off their phone rather than demanding the stored international form. It ends at the same erasure everything else uses, so there is no second opinion about what being forgotten means, and it keeps the one thing an erasure must keep: the record that this person asked not to be messaged, without which they would be messaged again the next time they typed the same number into a checkout. A number that could not be read, a number nobody has, and somebody who had already been erased get three different answers, because the first means try again and the second means stop looking.

- **A recovery can now be worked, not just watched.** The queue could be read in wp-admin and only acted on with curl -- and three of the four things worth doing to a recovery did not exist anywhere. A recovery's own screen now offers all four. **Try it again** puts a failed recovery back in the queue; it sends nothing itself, and consent, opt-outs and quiet hours are still checked before anything reaches anybody, so a customer who opted out since the failure is not messaged. Only a recovery that actually failed can be retried, because failing means the machinery could not, while recovered, expired, cancelled, opted-out and invalid each carry a decision about the customer and stay closed. A step that has already used its three attempts is refused rather than quietly queued to fail again, and the refusal says so. **Stop the links working** kills the links already sent without stopping the recovery, for a link that has been forwarded or posted somewhere public. **Never message this customer again** records an opt-out taken by telephone, doing exactly what the unsubscribe link does: every contact detail the customer has given, not merely their phone number, and every open recovery of theirs, not merely this one. The queue's row action only opens a recovery and changes nothing, because a row action is a link and a link that cancels somebody's recovery gets fetched by whatever follows links -- a prefetcher, a crawler, the antivirus proxy that opens every URL in an email.

- **The API can now answer what is being watched, and what may be sent.** Two routes the documentation had described for three releases did not exist: `/integrations` and `/templates`. The first answers the question somebody running a hundred shops actually asks -- which of them are recording anything -- and answers it with the verdict itself rather than the facts you would have to combine to reach it, because an integration can be installed, switched on and still recording nothing when the workspace's plan does not include it. The second lists the WhatsApp templates the workspace has had approved, each marked with whether RecoveryFlow can actually send it; one needing an image header or a carousel is listed and marked rather than hidden, because a merchant who cannot find the template they approved last week concludes the connection is broken. Neither route works its answer out for itself -- both read the same source of truth the screens read -- and neither writes anything, because a second way to write a setting is a second set of rules about what a valid setting is.

- **The background passes can be run from the status screen, by somebody with no shell.** "It has stopped sending" is the support call this plugin will get most often, and until now the only honest way to answer it was WP-CLI -- which a merchant on shared hosting does not have. Waiting an hour for the scheduler is not an answer either, because it cannot tell a scheduler that never fires apart from a queue with nothing eligible in it. The status screen now has a button that runs all five passes once, in the foreground, using exactly the code the scheduler uses rather than a copy of it, and then says what each pass did. A pass that could not take its lock is reported as skipped rather than as having found nothing -- the opposite diagnosis, on the one screen somebody is reading to find out why nothing is happening. It states plainly, before it is pressed, that the dispatch pass is one of the five, so it really does send and really does bill. Running the passes needs the permission to work the queue, not merely the permission to read the status screen: being allowed to see how a shop is doing is not the same as being allowed to make it message its customers.

- **RecoveryFlow can be worked from a terminal.** `wp recoveryflow status` reports every health check and what each background pass last did, and exits non-zero when something is stopping it working, so a monitoring script can watch it. `wp recoveryflow tick` runs the passes in the foreground -- the real scheduler's own code, under the real locks and the real time budget -- which is the only honest way to answer "it has stopped sending". There is also `journeys` for the queue and `sources` for the integrations. Customer contact details are masked with no flag to unmask them: anybody who can run WP-CLI can already read the database, so an unmasked column would protect nothing and would add a route to phone numbers through shell history and CI logs that no audit trail covers.

- **The example for developers building their own integration is now a real file that the tests run.** It lives at `src/Integration/Custom/Example_Source.php`, is never registered and never runs, and is linted, type-checked and instantiated against the real interfaces -- so it cannot describe an API the plugin does not have. `Abstract_Source` gained `report()` and `report_completed()`, and the registry now hands out what an adapter's constructor needs, so somebody writing an integration never has to reach into this plugin's container.

- **Gravity Forms is the second thing RecoveryFlow can recover.** It watches two things, deliberately unalike. A **save-and-continue draft** is the clearest abandonment signal this plugin gets anywhere: a shopper leaving a basket is inferred, but somebody pressing "Save and continue later" has said it out loud and been handed a link back to their half-finished form -- and then never heard about it again. An **entry whose payment never went through** is the opposite: they finished, and the money did not arrive, which is a refused card or a closed gateway tab and the case where a reminder most often completes the sale. Nothing is rebuilt from a snapshot; Gravity Forms holds the form itself and hands it back on its own resume link. Which fields hold the phone, email and name are read from the form's own definition by field type, because Gravity Forms has no fixed key for any of them and a merchant may rename every label. Forms with neither a phone nor an email field are skipped, spam and trashed entries are left alone, and a form that takes no money is never chased -- submitting one is the whole point of it. Included with the WA.cr Scale plan and above.
- **It also finds what happened before it was installed.** Hooks only ever tell you about the future, so a merchant switching this on for a site with four hundred unpaid entries would have got nothing from any of them. The background pass now reads entries created since where it last stopped, applying the identical rule the live path applies -- from the same code, so a backfill cannot end up chasing exactly the people the live path decided to leave alone. It looks back thirty days on a site's first pass rather than through the whole history.

- **Integrations can be switched off, and each one now has a settings section of its own.** Whether a source was switched on was read on every request from the first release and written by nothing: there was no control anywhere, so a merchant could not stop RecoveryFlow watching a system without deactivating the plugin that provided it. Every registered integration now has a section on Settings &rsaquo; Integrations -- a switch, plus whatever settings the integration itself declares. Those fields go into the same settings tree as everything else, so an integration cannot ship a field that saves without being validated, and each one keeps its own address for a deeplink.

- **A source that has no hooks to push from is now actually asked.** `Pollable_Source_Interface` shipped with the first slice, was documented in two places, and nothing in the plugin ever called it: an integration built on it would have compiled, passed every check, registered itself on the Integrations screen and then sat there reporting nothing, for ever. The Evaluate pass now asks each pollable source for a bounded page of what has appeared since it last looked, remembers where it stopped so a large backlog drains across successive passes rather than being rescanned from the top, and drops a source that throws for that run without losing its place -- one broken integration cannot stop the others.

- **The Auto Flow hook can be proved before a real basket depends on it, and there is a recipe for the flow itself.** The hand-off path works on every WA.cr plan, and everything that matters about it happens somewhere else: a merchant pasted an address and then had to go and build the thing that receives it with no statement anywhere of what would arrive. The settings screen now writes the whole payload down, key by key, next to the address -- and because WA.cr turns each one into a variable named hook_ plus the key, that list is the list of variables the flow will find waiting for it. Beside it is a button that sends one test push. It says plainly that this really runs your flow, because a webhook trigger fires on anything that reaches it, and the test carries no phone number so a flow that goes on to send has nobody to send to.
- **Opting out here can now opt somebody out in WA.cr too.** A customer who uses the unsubscribe link is asking the shop to stop, not a WordPress plugin. Switched on, this also marks them as opted out in your workspace, which takes them out of broadcasts and any campaign built from a segment. It does not stop a message sent directly through the WA.cr API or named by an Auto Flow, because those never check the flag -- so the setting says that rather than implying a switch it does not have. It is off until you turn it on, it needs the contacts:write permission, and it never delays or affects the opt-out itself.
- **A diagnostic report you can read before you send it.** The status screen carries a plain-text summary of this install -- versions, settings, what each health check said, how each background pass went -- built to be pasted into a support conversation. It holds no API key in any form, not even its length; no Auto Flow hook address, which is a credential and not a setting; no customer details; and nothing out of the logs. It is assembled from a list of things allowed in rather than by removing the bad parts, so anything added later is absent until somebody decides otherwise.

- **Templates are chosen from a list, and each blank in one says what it is.** A send step used to be a box to type a template name into, checked only when the message went out. It is now a list of the templates WA.cr has approved, and once one is chosen RecoveryFlow shows each blank using the template's own words -- "Hi ____ , your basket is waiting" -- with a list of what can go there: the customer's first name, what the basket comes to, the link that restores it. A template RecoveryFlow cannot send, because it needs an image header or a carousel, is listed and says so at the moment you pick it rather than failing hours later against a customer who received nothing. A template you chose before and have since removed stays on the list, marked, so a save cannot quietly send a different one. Where the list cannot be fetched -- no permission, no network -- the box comes back, and says why.

- **A recovery sequence can now be built without writing any.** The Workflows screen has an editor: each step is a panel with a plain-language choice in it -- check that the order has still not been placed, wait 2 hours, send a template over WhatsApp or email -- and steps are added, removed and reordered with ordinary buttons. There is no JavaScript in it at all, so it behaves the same way with scripts blocked as with them running, and every choice is a list rather than a box to type into: the workflow you build on the screen is one the plugin will accept, instead of one it tells you off about after you press Save. A save that is refused hands your work back rather than replacing it with the last version you saved.

- **The workflows a site runs are now visible, and readable.** RecoveryFlow has always installed two -- one that sends from WordPress and one that hands the recovery to a WA.cr Auto Flow -- and there was nowhere to see either. There is now a Workflows screen, and each one is shown as its steps in order, in words: "Waits 1 day before going on", "Checks that the order has still not been placed. If not, the recovery stops and is recorded as recovered." A workspace whose plan does not include sending from WordPress sees its workflows rather than an empty screen, is told plainly why they are read-only, and can still edit the hand-off workflow, which needs no API key and works on every plan.

- **Switching RecoveryFlow on now leads somewhere.** Activation opens a setup screen whose single step is connecting a WA.cr workspace -- the one thing the plugin cannot do for itself. Entering the key saves and checks it in one action, so a merchant is told which workspace they connected rather than being left holding a key of unknown quality. It is offered once, never during a bulk activation of several plugins, and never to somebody without the permission to act on it. Skipping is offered plainly, because abandoned baskets are already being recorded and skipping costs nothing.
- **A WA.cr plan too small for the developer API is no longer reported as a broken connection.** A workspace below Scale cannot call the developer API, and asking it to answers with a refusal -- but that refusal arrives *after* WA.cr has authenticated the key, so it is positive proof the key is good. RecoveryFlow now says so: the key is accepted, this plan does not include sending from WordPress, and here is the hand-off to a WA.cr Auto Flow, which works on every plan and needs no API key at all. Telling a merchant their working key had failed would have dead-ended the one path that was open to them.

- **Being forgotten also stops a recovery already in flight.** Erasure previously stripped a journey's contents and revoked its links but left a scheduled journey sitting in the queue until it expired. Nothing would have been sent -- an anonymised customer is refused by the eligibility rules -- but the recoveries screen went on showing work being done for somebody who had asked to be forgotten, and every background pass kept picking it up to decide again that it must not.
- **Expandable settings panels are remembered per person rather than per browser**, so the shape of a screen follows somebody from a laptop to the shop's back-office machine. Which panels were open is rendered into the page by PHP, so one that should be open is open in the first paint rather than springing open a moment later; the browser's own storage is the fallback when that cannot be saved.

- **RecoveryFlow has admin screens.** An overview that leads with whatever needs attention rather than a wall of ticks; the recovery queue as a standard WordPress list with filtering, sorting, searching and paging; one screen per recovery; the integrations RecoveryFlow can watch; and a system status screen. All built from core WordPress components, with no framework and no build step.
- **The queue is safe to leave open on a shop counter.** Customer names, phone numbers and email addresses are shortened everywhere on the list, and there is deliberately no way to unmask a whole list at once. A single recovery's own screen can show the details in full to somebody holding the reveal permission, who has to ask for it -- and who is told, before and after, that the viewing is recorded.
- **Every status check tells you what to do and links to where to do it.** "Email cannot be sent yet" arrives with the box to type the postal address into, even though that box is on a different tab. Each result is stated in words in a column of its own -- Working, Check this, Stopped -- so a screenshot pasted into a support thread keeps its meaning. The screen and the REST endpoint read the same checks, so they cannot give different diagnoses of the same site.
- **A recovery's own screen answers the support call.** What was in the basket, who it was sent to, what was actually sent and when, and on what basis this shop believed it was allowed to send it. Times are shown in the site's own timezone rather than the UTC everything is stored in.

- **RecoveryFlow has a REST API, under the shared KDC namespace.** Six routes at `/wp-json/kdc/v1/wacr/recoveryflow/`: the journey queue and one journey in full, cancelling a journey, system status, a WA.cr connection test, the settings, and a per-person record of which panels somebody had open. Every route demands a named capability rather than merely a logged-in user -- a subscriber is logged in, and these carry customer contact details and the ability to cancel somebody's recovery. A refusal says which permission was missing, so "why can my shop manager not see this" has an answer.
- **Customer contact details are masked by default, and revealing one is recorded.** A journeys list is a screen left open on a shop counter, so a column of phone numbers should not be readable by whoever walks past. The full value needs both the reveal permission and an explicit ask -- holding the permission does not unmask a listing nobody asked to unmask -- and asking writes an audit row. A journey that has been erased is described as erased rather than returned as blanks, and a reference that never existed and one that has been erased get the identical answer, so the endpoint cannot be used to confirm that a given reference used to be real.
- **The system status screen says what to do, not just what is wrong.** Each check reports whether it passed, a sentence a shopkeeper can act on, and a link straight to the setting that fixes it -- so "email cannot be sent yet" arrives with the box to type the postal address into. Severity is always accompanied by that sentence and never carried by a colour alone. The WA.cr connection is only tested when somebody presses the button; checking a credential on every page load would make the shop's own admin depend on somebody else's uptime.
- **The settings API is read-only, and never returns the API key.** Not masked, not partially, not as a length: an endpoint that reports facts about a secret helps somebody guess it. Saving still goes through core's options.php, because a second way to write the same option would be a second set of rules about what a valid setting is, and the one that disagreed would be the one nobody tested.

- **A customer can ask what this shop holds about them, and to be forgotten.** RecoveryFlow now appears in WordPress's own privacy export and erasure tools. The export answers with the recovery record, every contact detail held, the full consent history -- what was agreed to, on which channel, from where, and the exact wording -- and each unfinished order with the reminders sent about it. Values are exported in full rather than masked: masking exists to stop a passer-by reading a shop screen, and has no place in a copy of your own data.
- **Being forgotten does not switch the reminders back on.** An erasure removes names, the readable phone number and email address, basket contents, notes, the session key and the WA.cr contact id, and revokes every recovery link already sent so one sitting in somebody's message history stops working. It deliberately keeps the one-way hash of each contact detail, because that hash *is* the suppression list: delete it and the shop forgets that this person asked not to be messaged, and messages them again the next time they type the same number into a checkout. Erasing an opt-out is not a privacy improvement, it is the failure the opt-out exists to prevent. The person is told exactly this, in the message WordPress shows them. Amounts and dates are kept as the shop's own accounts.
- **Data nobody has a reason to keep is now removed on a schedule, including the person.** The daily clear-out already stripped what a finished basket contained; it now also anonymises the customer behind it once every one of their journeys has been finished for longer than the retention period. Only customers with nothing still running are touched, so somebody who came back after six months is not anonymised in the middle of being messaged. Erasure and retention share one implementation, because two would eventually disagree about what "erased" means and the half nobody was looking at would be the one that forgot something.

- **Settings have a screen, so a merchant can finally clear the email blockers.** RecoveryFlow's settings existed and were readable only from the database. There is now a settings screen -- six tabs of sections, cards and expandable panels, built from core WordPress components with no framework and no build step -- and every one of the plugin's stored settings has a control on it. Most consequential: the Channels tab lists exactly what is standing between this site and a lawful recovery email, in plain language, each with a link straight to the control that clears it. The unsubscribe-window blocker is cleared on a different tab entirely, which is why it is a link and not a sentence. Settling all three makes email permissible and says so; it does not switch email on, and the screen says that too.
- **Every setting has a stable address that can be linked to.** `…&tab=channels&section=email&field=merchant_postal_address` opens the right tab, scrolls to the control, outlines it and moves the keyboard cursor into it -- so a notice, a status check or a support reply can point at one box rather than describing where to find it. The outline and the focus do that work; colour is never the only thing marking it. Without JavaScript the URL fragment still lands on the right control, and every setting is still present and editable: conditional fields are rendered and then hidden, never omitted.
- **The screen is built to WCAG 2.2 AAA where that is achievable.** Help text is associated with its control rather than merely sitting near it, groups of choices are real fieldsets so they are announced as one question, tick-box targets are 44px rather than 16px, expandable panels are native `<details>` so they keep the keyboard behaviour a hand-built one loses, results are announced through `wp.a11y.speak()`, and an irreversible option asks before it is switched on and never when it is switched off.

- **An abandoned WooCommerce cart now becomes a recovery journey on its own.** The adapter watches the cart, picks up a shopper's phone number and email as they fill in checkout on both the classic and the block checkout, records whether they agreed to be messaged, and writes one row per shopping session rather than one per change. On the classic checkout, leaving the phone or email field -- or ticking the consent box -- asks WooCommerce to re-read the form there and then, so a shopper who gives their details and then leaves is actually recorded. Previously the form was only re-read if they went on to change an address, country, coupon or shipping method, which is exactly the shopper who does not: WooCommerce watches its address fields and does not watch phone or email. Nothing is sent anywhere by this; it asks WooCommerce to make the request it already knows how to make, on its own nonce, and if the small script involved fails to load the checkout behaves exactly as it did before. Everything it does is wrapped so that a failure in recovery tracking can never break somebody's checkout.
- **A shopper who logs in halfway through keeps one cart, not two.** WooCommerce gives a guest a new session identity when they sign in, and without following that the same basket would be tracked twice and the customer would receive two reminders for it.
- **Recovery runs in the background, in batches, and survives being run twice at once.** Five stages -- find, send, check for replies, expire, tidy up -- on Action Scheduler where WooCommerce provides it and on WP-Cron where it does not. Neither scheduler promises a job never overlaps itself, so every stage takes a database lock first and every write states the state it expects to find.
- **A message is reserved before it is sent, so a retry cannot send it twice.** The messaging API has no way to recognise a repeated request, which means an ordinary retry would deliver the same reminder again and bill the merchant for it again. A request that failed before it opened a connection is retried; one that timed out after the request was written is recorded as unknown and settled by reading the conversation back, never by sending again.
- **Merchants describe recovery as a sequence of steps.** Wait, check a condition, send -- validated against a strict schema with no code execution anywhere in it, and pinned per journey, so editing a workflow never changes what a customer already part-way through it will receive. Two sequences ship: one that sends from WordPress, and one that hands the journey to a WA.cr Auto Flow.
- **Each step chooses its own channel.** An action step carries `whatsapp` or `email`, so "WhatsApp after an hour, email the next day" is something the merchant builds rather than a fallback order the plugin decides for them.
- **Recovery links restore a cart without destroying the one the shopper already has.** Items are merged, anything out of stock or no longer purchasable is skipped, quantity limits are respected, and following somebody else's link is refused outright. Links are unguessable, stored only as a hash, and expire.
- **Email reminders cannot be switched on until the site can send them lawfully.** A recovery email is commercial mail -- not a receipt, not a reply -- so it has to carry the sender's real postal address and an unsubscribe that keeps working for thirty days. Neither is something a plugin can supply, so RecoveryFlow refuses the email channel instead: the merchant enters their postal address and its country, and sets the recovery link lifetime to at least thirty days, because the unsubscribe link in an email is that same link. Only then is the channel available. This is a second gate rather than the switch; email still defaults to off and turning it on is still the merchant's decision, but a setting written by WP-CLI, a migration or another plugin can no longer start unlawful mail on its own. The address is stored exactly as it is typed and is never translated or reformatted -- an address is laid out according to its own country, not the language of whoever is reading the settings screen, which is why the country is asked for separately rather than guessed from the text.

- **Opting out takes a deliberate action rather than a click.** WhatsApp fetches every link in a message to build its preview, so an opt-out that worked on a plain visit would unsubscribe every recipient the moment the message was delivered. The link shows a confirmation page and nothing changes until the shopper confirms it. Clicks from preview fetchers are not counted either.
- **Messaging stops the moment an order is placed, and stays stopped.** Placing an order pauses the journey rather than completing it; only payment completes it. A failed payment hands the journey back exactly once, because somebody whose card was declined twice does not want a third reminder. Every order hook claims a receipt first, so a gateway that calls back twice moves the journey once.
- **The plugin activates cleanly on any WordPress 6.5 site running PHP 8.0, with or without WooCommerce.** Main plugin file with header, `KDC_WACR_RECOVERYFLOW_*` constants, a requirements gate that explains what is missing instead of failing, and boot on `plugins_loaded`. The gate hands back machine-readable rows and builds its sentences only when the notice is rendered -- asking for a translation on `plugins_loaded` is too early for the text domain, and WordPress 6.7 and above warns about the early load and returns the untranslated string anyway.
- **Classes load without Composer at runtime.** PSR-4 autoloader for the `WAcr\RecoveryFlow` namespace and a small service container.
- **Activation creates the plugin's ten database tables and can upgrade them in later versions.** Activator, Upgrader and a versioned dbDelta schema; lock rows are seeded at install so background stages can take row locks from the first run. Updating installs everything activating does, because WordPress does not run a plugin's activation hook when it is updated -- a site that already had RecoveryFlow switched on would otherwise come out of an update with the tables and the schedule but no workflows, and quietly recover nothing.
- **Access is controlled by dedicated capabilities rather than `manage_options` alone.** Six `recoveryflow_*` capabilities installed on activation, re-applied whenever the capability version changes, and re-granted whenever any other plugin activates -- so installing RecoveryFlow before WooCommerce does not leave shop managers with no access.
- **A per-site random hash key is minted on activation** so phone and email hashes are keyed to the site and cannot be looked up across installations.
- **Uninstall cleans up after itself.** Credentials, the hash key, capabilities and scheduled actions are always removed; tables and options are removed only when "Delete all data on uninstall" is enabled.
- **The plugin is translation-ready.** Text domain `kdc-wacr-recoveryflow` and a `.pot` template in `languages/`.
- **Every string a person can read is translatable, and it stays that way as the plugin grows.** Short status labels carry a `_x()` context, because "New", "Replied" and "Failed" are one word each and cannot be translated correctly by a language that inflects for gender or number without knowing they describe a recovery journey. The shortened customer name is a format string rather than a concatenation, so a translator controls name order and whether an initial takes a full stop. The WA.cr hostname was lifted out of the environment labels into a placeholder, so no one is invited to translate a domain name. `docs/internationalization.md` states the rules; `composer i18n:audit` and `composer i18n:check` enforce them in CI alongside PHPCS.
- **Contributors get the full toolchain on `composer install`.** Composer scripts for linting (WordPress Coding Standards with PHPCompatibilityWP), static analysis (PHPStan), unit and integration test suites (PHPUnit), pa11y-ci for accessibility, a `.wp-env.json` for a local WordPress with WooCommerce, and a CI workflow that runs them.
- **The documentation set exists from day one.** `readme.txt` and the `docs/` folder: architecture, integrations, developer API, security, privacy, WA.cr integration, testing and accessibility.
- **`readme.txt` states plainly that an active WA.cr account is required.** The requirement now appears in the short description, in a dedicated section at the top of the description, in the External services disclosure, as the first installation step and as the first two FAQ entries, together with what does and does not work without an account. The short description was trimmed to the 150-character limit the plugin directory enforces, and `docs/` links point at the repository because `docs/` is excluded from the distributed build.
- **A recovery journey can only make moves that make sense.** The state machine is declared in one place, including the awaiting-payment state that stops messaging the moment an order is placed and hands the journey back exactly once if the payment then fails.
- **A phone number typed at checkout is turned into a real international number, or refused.** The normaliser uses the billing country as its hint, handles trunk prefixes and international prefixes, and refuses rather than guesses when it cannot tell -- a national number promoted to the wrong country would deliver a customer's cart reminder to a stranger.
- **Recovery links are unguessable and stored only as hashes.** 32 random bytes, checked against a pattern before any database lookup, so a scanner costs a regular expression rather than a query.
- **Talking to WA.cr goes through one client.** Connection test, sender and template lookups with caching, template sends, conversation reads, contact lookup, and the Auto Flow hand-off, with the API key encrypted at rest and never rendered back.
- **A failed send is classified accurately enough to retry safely.** A connection that never opened is retried; a request that timed out after it was written is recorded as unknown and reconciled before anything is sent again, because the messaging API has no idempotency key and a blind retry would message the customer twice and bill the merchant twice.

### Fixed

- **An order stopped nothing.** The ledger that stops the same event being handled twice never let the FIRST caller through on a real database, so every order event was discarded as a duplicate of itself: placing an order did not stop the reminders, and paying did not mark the recovery recovered or attribute the revenue. It is the plugin's central promise, and it was broken on every real install. The cause is narrow and worth knowing: the ledger's table is keyed on the event's own name rather than a counter, so the database returns no new row number, and the code read that missing number as "somebody else got there first". Because the number is left over from whatever was written previously in the same request, it was worse than simply broken -- sometimes it let *everybody* through and there was no protection at all. Nothing in the test suite could see it, because the stand-in database used for testing handed back a row number for every write.

- **A basket value read like a database column.** The recoveries queue and a recovery's own screen showed a £18.99 basket as "18.9900 GBP" -- correct to four decimal places, which is how the amount is stored so that odd unit prices do not lose money, and not how anybody reads money. Amounts are now shown to two places, in the site's own number format.


- **Two background statements were reading the wrong index on a large site.** Measured against a seeded database, closing stale events chose an index answering only one of its three conditions and examined about seventy-four thousand rows every pass to close five hundred, and claiming a batch of work sorted the matching rows in memory to take fifty. Both are now a read that uses the index built for it followed by a write addressed by primary key. The claim is still atomic -- the write re-checks the lease, so where two background runs pick the same journeys the second claims none of them. The honest measurement: **no difference at a hundred thousand events, and three times faster at three hundred and fifty thousand**, because the cost is in rows examined and that only begins to bite once the table is large enough for the wrong index to matter. It also removes an `UPDATE ... LIMIT` that MySQL treats as unsafe for statement-based replication.

- **The developer documentation described an API that did not exist.** Its example custom source called a constructor with the wrong signature and two methods that had never been written, and it said so confidently for three releases, because an example in a Markdown file is checked by nothing. The document now quotes a real file, and the test suite fails if the documentation calls a method that does not exist -- a check that found an invented method in its own first draft.

- **The Integrations screen said an integration was recording baskets when it was not.** A source that is installed and switched on is still excluded when the WA.cr plan does not include it -- its hooks are never attached -- and the screen, which worked its answer out from only the first two of those three facts, announced "Active. Abandoned baskets from here are being recorded." about an integration that was watching nothing. It now asks the same method the behaviour asks, so a card and a hook cannot disagree, and a plan that excludes an integration says so in those words.

- **"Opting out in WA.cr also stops reminders from here" now actually does something.** The check behind it was built, and running: RecoveryFlow asks WA.cr whether somebody has opted out before each reminder, remembers the answer for six hours, and sends anyway if WA.cr cannot be reached. What was missing is that nothing read the checkbox, so the setting said one thing and the plugin did another whichever way it was set. The checkbox now controls it, and it is on by default -- which is exactly what every site has been doing, so nothing changes for anyone. Switching it off means somebody who has told you to stop can still receive a cart reminder from this site, and the setting now says so.

- **The status screen reported zeroes for exactly the background passes that had done some work.** It read the stored figures in their raw form while treating each one as an object, which PHP answers with nothing at all. A pass that had never run was described correctly, from a fallback; a pass that had actually found baskets or sent reminders reported nothing processed, nothing failed and no last run. The one screen somebody opens when they suspect recovery is not happening was accurate only about the parts that were idle.

- **A workflow that cannot be saved now says what was refused, not just what is missing.** Pressing Save on a workflow with a send step in it, on a plan that does not include sending from WordPress, used to answer "No WA.cr API key is connected yet" and nothing more -- a true sentence about the stored key, and an answer to a question nobody asked. It now says the workflow was not saved, that a step of it sends from WordPress, why this site cannot do that, and that a step can hand the recovery to a WA.cr Auto Flow instead, which works on every plan.

- **A saved WA.cr key can now actually be connected, and the settings screen stops contradicting itself.** Entering a key and saving it left the screen saying "A key is saved" directly above "No WA.cr API key is connected yet". Both sentences were true of their own stored value and neither was true of the site: whether a key *works* is only learned by asking WA.cr, and nothing in wp-admin could ask. The status screen had been telling merchants to "use Test connection" since the admin screens shipped, and no such button existed anywhere. There is now one, on the WA.cr tab beside the key: it is an ordinary form that works with scripts switched off, and it says which workspace the key belongs to and what it may do. A key that is saved but not yet checked is now described as unchecked rather than as absent.
- **Replacing the API key no longer leaves the previous workspace's answer standing.** What RecoveryFlow had learned about a credential -- which workspace, which permissions, whether the plan includes the developer API -- was only discarded when a key was *removed*, not when a different one was saved over it. The screen could report being connected to one workspace while holding another's key, and the plugin could go on offering to send directly on permissions the stored key may not have had.

- **Unsubscribing now actually stops the reminders for somebody who gave an email address and no phone number.** Suppression is recorded against each contact detail separately, and the opt-out only ever recorded one against the phone number. For a shopper reachable only by email that recorded nothing at all, while the page told them the reminders had stopped; for a shopper with both, it left the address reachable. Confirming now suppresses every identity the person has. The two public pages no longer name WhatsApp either, because what the button switches off is the reminders, not one way of delivering them.

### Security

- **Nothing personal reaches a log.** A redactor drops known fields and masks phone numbers, email addresses, credentials and recovery links inside free text, including error strings that arrive from elsewhere.
